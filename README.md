# RepairCalc

RepairCalc — микросервис для расчёта ремонта и подбора строительных материалов.

- `app/` — backend API и frontend приложения.
- `llm/` — отдельный HTTP-сервис интеграции с локальной LLM.

Сервисы запускаются в Docker и общаются по HTTP внутри Docker-сети. API приложения будет доступно внешним клиентам.

## Загрузка новой JSON-выгрузки в PostgreSQL

```sh
./scripts/import_products_json.sh
```

Потоково читает `products_final.json` и атомарно заменяет схему и данные
`public.products` в БД `repaircalc`. Адрес БД задаётся через `DATABASE_URL`
или вторым аргументом скрипта. Подробности формата и схемы — в
[parser/README.md](parser/README.md).

## Интеграция с каталогом Максидома

Модуль `repair_calc::catalog` использует существующие модели `src/models/`.
Он предоставляет HTTP-клиент `CatalogClient`, загрузку всего выбранного поддерева
`synchronize` и сохранение снимка `synchronize_to_file`. Контракт взят из раздела
«Источники данных» документа `.docx` в корне проекта; примеры в документе иллюстративные.

### Запуск синхронизации

Укажите адрес API-стенда, выданный организаторами (origin, без `/api`; допускается
префикс развёртывания, например `https://host/stand`). В документе адрес не указан.

```sh
export MAXIDOM_BASE_URL="https://<адрес-стенда>"
cargo run --bin catalog-sync
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MAXIDOM_BASE_URL` | обязательная | Адрес стенда без `/api` |
| `MAXIDOM_API_TOKEN` | отсутствует | Необязательный Bearer-токен, если нужен на стенде |
| `MAXIDOM_LOCALE` | `ru` | Язык дерева и товаров |
| `MAXIDOM_ROOT_CATEGORY_ID` | `1` | Корень выбранного поддерева |
| `MAXIDOM_DEPTH_LEVEL` | `20` | Глубина дерева |
| `MAXIDOM_PER_PAGE` | `20` | Размер страницы товаров; максимум API не заявлен |
| `MAXIDOM_TIMEOUT_SECONDS` | `30` | Таймаут одного HTTP-запроса |
| `MAXIDOM_SNAPSHOT_PATH` | `data/catalog.json` | Путь результата |

Запуск сервера через `cargo run` по-прежнему работает. Синхронизация запускается
отдельной командой; её можно повторять вручную или по внешнему расписанию.

### Что загружается

- `GET /api/catalog/categories/tree` — дерево выбранного подкаталога.
- `GET /api/catalog/categories` — сведения и описания категорий, сгруппированные
  по `parent_id` и уровню из дерева.
- `GET /api/catalog/products` — все страницы до `meta.last_page` для корня
  и каждой категории дерева, включая промежуточные. Запрос использует
  `include_subsections=0`, `include_categories_tree=1`, нумерацию страниц от 1.
- `GET /api/catalog/products/{id}` — полная карточка каждого уникального товара
  по Bagisto `id`, включая `description`, `weight`, `characteristics`.
- `GET /api/regions` — справочник для сопоставления `stocks[].region_id`.

Снимок содержит время завершения в Unix-секундах, параметры области синхронизации,
дерево, плоские категории, товары и регионы. Объекты индексируются по `id`;
`sku` и `cod_good` сохраняются отдельно как строки. Повторы товаров между
страницами и категориями объединяются, подробная карточка запрашивается один раз.
Данные полной карточки имеют приоритет; контекст категорий дополняется из списка.
Фильтры `properties` не присваиваются товарам как характеристики. Значения цен,
в том числе `result_price`, сохраняются из API без пересчёта акций. Модели сейчас
хранят цены как `f64`; для будущих денежных расчётов требуется десятичный тип.
Неподтверждённые параметры регионального контекста в запросы не добавляются.

Синхронизация последовательная. Клиент переиспользует соединения, проверяет HTTP-статус
и JSON, повторяет GET при ошибке соединения, таймауте, HTTP 429 или 5xx до двух раз.
Задержка — 0,5 и 1 секунда; числовой `Retry-After` учитывается до 30 секунд,
при большем значении клиент возвращает ошибку без досрочного повтора. Перенаправления
не выполняются. Отсутствующая или некорректная пагинация вызывает ошибку вместо
сохранения частичного каталога; защитный предел — 10 000 страниц на категорию.
Настройки повторов и предела доступны через `ClientConfig`.

Новый снимок публикуется атомарной заменой файла только после успешной загрузки
всех данных. При сбое старый файл сохраняется. Удалённые из источника товары исчезают
после следующей успешной синхронизации. Снимок заменяет только выбранную область:
для разных корней используйте разные файлы. Это полная повторная загрузка,
без инкрементального обновления. Глубина ограничивает область обхода:
пустой `children` при малой глубине не гарантирует отсутствие подкатегорий.
Для полного каталога задавайте достаточную глубину по данным стенда.

### Использование из Rust

```rust,no_run
use repair_calc::catalog::{CatalogClient, ClientConfig, SyncOptions, synchronize_to_file};

# async fn example() -> Result<(), Box<dyn std::error::Error>> {
let config = ClientConfig::new(std::env::var("MAXIDOM_BASE_URL")?);
let client = CatalogClient::new(config)?;
let snapshot = synchronize_to_file(&client, &SyncOptions::default(), "data/catalog.json").await?;
println!("{} products", snapshot.products.len());
# Ok(())
# }
```

Отдельные методы клиента: `category_tree`, `categories`, `products_page`,
`products` (все страницы), `product`, `regions`. Снимок можно прочитать через
`CatalogSnapshot::load`. Хранение в PostgreSQL и REST-ручки приложения в этот
модуль не входят; его можно вызвать из будущего сервиса синхронизации.

Проверки на локальном HTTP-стенде без обращения к внешнему API:

```sh
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
```

Тесты проверяют параметры всех пяти ручек, пагинацию, загрузку карточек,
дедупликацию, обновление снимка, сохранность прежнего файла при сбое,
HTTP-ошибки, повторы, таймауты, неверные ответы, локаль и авторизацию.
