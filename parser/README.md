# Импорт каталога

## Новый JSON → PostgreSQL

Из корня проекта:

```sh
./scripts/import_products_json.sh
```

По умолчанию читает `products_final.json` и подключается к `dbname=repaircalc`.
Для другой базы задайте `DATABASE_URL` или передайте DSN вторым аргументом:

```sh
./scripts/import_products_json.sh /path/to/products.json 'dbname=repaircalc host=localhost user=myuser'
```

Требуются Rust/Cargo, клиент `psql` в `PATH` и права на создание/замену таблицы
в схеме `public`. Аутентификация — штатная PostgreSQL: peer, `.pgpass`, переменные
libpq. Пароль лучше хранить в `.pgpass`, а не передавать в аргументах.

Формат входа — объект `{"products": [...]}`. Чтение потоковое через Serde visitor:
в памяти находятся буфер 64 КиБ и текущий товар, массив целиком не загружается.
Данные передаются в `psql` через потоковый `COPY FROM STDIN` с обратным давлением
через pipe. Денежные значения разбираются без промежуточного `f64`.

Схема в [sql/products_json.sql](sql/products_json.sql) повторяет поля нового JSON:

| Столбец | PostgreSQL |
|---|---|
| `id` | `bigint`, первичный ключ, положительный |
| `cod_good` | `text`, сохраняет ведущие нули |
| `name` | `text NOT NULL` |
| `marketing_description`, `url_key`, `currency`, `unit`, `description` | `text` |
| `price`, `weight` | `numeric`, без округления до заданного масштаба |
| `brand`, `collection`, `country`, `categories` | `jsonb`, объект или SQL NULL |
| `characteristics` | `jsonb`, массив или SQL NULL |

У характеристик поле `code` не требуется: сохраняется исходный массив объектов
с `name` и `value`. Вложенные сущности сохраняются целиком. JSON `null`
у необязательных полей становится SQL NULL; пустые строки, массивы и объекты
отличаются от NULL. Дополнительные поля товара вызывают ошибку, чтобы изменение
формата не приводило к незаметной потере данных. Порядок ключей JSONB не сохраняется.

Есть B-tree индекс по `cod_good`, GIN индексы по `categories` и `characteristics`.
Например:

```sql
SELECT id, name, price, brand->>'name' AS brand
FROM public.products
WHERE categories ? '507';

SELECT id, name
FROM public.products
WHERE characteristics @> '[{"name":"Тип древесины","value":"ольха"}]'::jsonb;
```

### Замена старого каталога

Каждый запуск **полностью заменяет `public.products`**, включая схему, старые
столбцы и товары, отсутствующие в новом файле. Все операции выполняются в одной
транзакции: создаётся `public.products_json_import`, загружаются строки, проверяются
ограничения и количество, создаются индексы. Затем старая таблица удаляется,
новая переименовывается в `products`, выполняется `COMMIT`. Параллельные импорты
сериализуются advisory-lock, совпадающим с блокировкой старого XML-импортера.
Читатели старой таблицы могут кратковременно блокировать финальную замену.

Обрыв/ошибка JSON, пустой каталог, дубли ID, неверный тип, ошибка COPY или SQL
откатывают транзакцию: старая таблица остаётся на месте. Проверяется конец JSON
и отсутствие лишних данных после него. Не используется `DROP ... CASCADE`:
зависимые представления/внешние ключи остановят импорт с откатом. Права,
триггеры и пользовательские индексы старой таблицы не переносятся; эта схема
предназначена для текущей отдельной таблицы каталога.

Перед первой заменой существующей схемы рекомендуется резервная копия:

```sh
pg_dump -Fc -d repaircalc -f backups/repaircalc-before-json.dump
```

Старая XML-утилита в `src/main.rs` сохранена для старого формата и старой схемы.
После миграции для загрузки товаров используйте новый JSON-импортёр.

## Проверки

```sh
cargo test --manifest-path parser/Cargo.toml
cargo clippy --manifest-path parser/Cargo.toml --all-targets -- -D warnings
```

Тесты проверяют потоковую обработку, точность десятичных чисел, строковые коды,
вложенные поля, экранирование COPY, ошибки callback, обрезанный JSON,
дублирование/отсутствие корневого `products` и изменение полей товара.
